# RFP: m5-system-panel

> Generated: 2026-09-26
> Status: Draft — later changes are recorded under Amendments
>
> English translation. The Japanese version (`docs/ja/m5-system-panel-rfp.ja.md`) is the primary document.

## 1. Problem Statement

Checking a Mac's load (CPU, GPU, memory, network) means opening Activity Monitor or a
menu bar item, which takes screen space from the work at hand or pulls the eyes away.
m5-system-panel turns an M5Stack BASIC on the desk into a small instrument panel
dedicated to one Mac and shows these values at all times. A resident app on the Mac
(the companion) measures them and sends them over the local network; the M5 only
draws, and its buttons only switch display pages.

The target user is a developer who wants to glance at their own Mac's load (first of
all, the maintainer).

This project replans m5-notify-deck (a general-purpose notification display over BLE),
withdrawn on 2026-09-25. Its code was discarded and is not reused. The lessons of the
withdrawal are recorded in organization ADR-023; this RFP is written to satisfy its
Phase 1 items 3 and 7.

## 2. Functional Specification

### Commands / API Surface

Two components.

| Component | Form | Role |
|---|---|---|
| M5 firmware | For M5Stack BASIC v2.7 | Draws the values it receives; buttons switch pages |
| Companion | macOS menu bar app (no Dock icon, no CLI) | Measures and sends; performs the M5's initial setup |

**M5 screen (320×240)**

| Page | Content |
|---|---|
| ① Overview | Current values and small trend graphs for CPU, GPU, memory and network in four quadrants |
| ② CPU | Overall usage trend (about 5 minutes) and per-core bars (P / E cores in different colours) |
| ③ GPU & memory | GPU usage trend, memory breakdown (app, wired, compressed), pressure, swap used |
| ④ Network | Up/down trend (auto-scaled), name of the interface in use |

- Buttons: A = previous page, C = next page, B = back to ① Overview. Button presses are never sent to the Mac.
- The M5 keeps 300 points of history at 1 s per point (only current values are sent).
- After 3 s without values it shows "waiting for data" and leaves a gap in the graphs;
  after N more minutes it dims the screen (so it does not stay lit while the Mac sleeps).
  Values arriving or a button press restore it.
- The device ID (a short random ID created at setup, e.g. `3F2A`) is always shown in a corner.
- If GPU values do not arrive (the Mac cannot read them), the GPU display is hidden.

**M5 setup mode**

- Entered when no Wi-Fi settings exist, or by **holding B while powering on for 3 s**;
  the latter first erases the stored Wi-Fi settings and key.
- Scans for nearby Wi-Fi once, **then** starts the setup Wi-Fi (SoftAP).
- The screen shows the setup Wi-Fi name (`m5-system-panel-<device ID>`), a one-time
  password (12 characters, new each time setup starts), and "Continue setup in the companion on your Mac".
- If it cannot join the home Wi-Fi, it shows "Cannot connect to Wi-Fi" and how to redo setup.
  **It never starts the setup Wi-Fi on its own** (so no Wi-Fi visible to others appears unannounced).

**Companion menu**

| Item | Content |
|---|---|
| Status | Connected (panel `3F2A`) / Searching / Not responding / Local network permission required (with where to grant it) / Not set up |
| Start setup | Shown only while an M5 in setup mode is on the same network; opens the setup window |
| Unregister panel | Deletes the stored device ID and key |
| Launch at login | Off by default (SMAppService) |
| Quit | |

**Initial setup flow**

1. The M5 enters setup mode and starts the setup Wi-Fi.
2. The user joins it from the Mac's Wi-Fi menu (password on the M5's screen).
3. The companion finds the M5 in setup mode and shows "Start setup" in its menu.
4. In the setup window, the user picks from the list of networks the M5 scanned (or types one), enters the password and saves.
5. The device ID and a key (256 bits) generated by the M5 are handed to the companion. The companion
   stores the key in the Keychain; the M5 stores the Wi-Fi settings and the key in NVS.
6. The M5 joins the home Wi-Fi; the Mac returns to its usual Wi-Fi. From then on they connect automatically.
7. The last step of the setup window explains how to remove the setup Wi-Fi from Known Networks.

### Input / Output

**Measurements (Mac → M5, every second)**

| Item | Content |
|---|---|
| CPU | Overall usage; per-core usage and core type (P/E) |
| GPU | Usage (absent when unavailable) |
| Memory | Used, installed, breakdown (app, wired, compressed), swap used, pressure (normal / warning / critical) |
| Network | Name of the primary interface; receive and send rates (B/s) |

**Communication**

- Discovery: the M5 advertises the Bonjour (mDNS) service type `_m5-system-panel._tcp`, with the
  device ID in the instance name and TXT record. The TXT record also says whether it is in setup mode.
- Connection: the companion opens a TCP connection to the M5 (outgoing, so no Mac firewall prompt).
- One line = one frame. The Mac sends measurements every second; the M5 returns an acknowledgement
  every second. If no acknowledgement arrives for 5 s the Mac shows "Not responding" and reconnects.
- **Authentication and encryption (normal operation)**: every frame is encrypted and authenticated
  with ChaCha20-Poly1305 (RFC 8439) using the key shared at setup. For each session both sides
  contribute random values, and per-direction session keys are derived with HKDF (RFC 5869).
  Nonces are per-direction counters and are never reused under the same key; the counter also
  rejects replays. Acknowledgements from the M5 are protected the same way, so the Mac can tell a fake panel.
- **During setup**: the network list, the Wi-Fi settings and the device ID and key are exchanged
  inside the setup Wi-Fi (WPA2, one-time 12-character password).
- The concrete frame format (text encoding, fields, version) is decided in the Phase 1 format
  specification and reviewed before implementation.
- The format version is checked at session start; on mismatch the menu shows "The M5 firmware does not match".

**Preventing cross-talk (several panels or Macs on one network)**

| Situation | Behaviour |
|---|---|
| Mac A with panel A and Mac B with panel B on the same LAN | Each Mac connects only to the panel whose device ID it received a key for at setup; other panels are ignored |
| Mac A connects to panel B by mistake | Panel B drops frames it cannot verify; its existing connection with Mac B stays up |
| A fake panel claiming the same ID | Its acknowledgements do not verify under the Mac's key, so the Mac never shows "Connected" |
| Two panels in setup mode at once | Each setup Wi-Fi has a different name, and each network holds only one panel |
| Moving a panel to another Mac | Redoing setup regenerates the key; the previous Mac's key becomes invalid |

- The M5 drops an existing connection in favour of a new one **only when the new connection's
  first frame verifies under the correct key** (needed for a Mac reconnecting after sleep).

### Configuration

- M5: no configuration file. Wi-Fi settings, device ID and key are stored in NVS by setup mode.
- Companion: device ID and key in the Keychain; "Launch at login" through SMAppService.
  The send interval (1 s) and network interface (the primary one, chosen automatically) are fixed; there are no settings.

### External Dependencies

- No external services, API keys or cloud.
- M5: libraries bundled with arduino-esp32 3.x (ESP-IDF 5.x) — WiFi, ESPmDNS, Preferences —,
  mbedTLS bundled with ESP-IDF (ChaCha20-Poly1305, HKDF), and M5Unified (official M5Stack).
  Setup is done by the companion, so no web server runs on the M5.
- Mac: Apple frameworks only (SwiftUI, Network.framework, CryptoKit, IOKit, Security, ServiceManagement).
- No community libraries (ArduinoJson included).

## 3. Design Decisions

**Languages and structure**

| Side | Choice | Reason |
|---|---|---|
| M5 | Arduino C++ + M5Unified, built with arduino-cli | Same approach as m5-clock and m5-vehicle-logger; the knowledge base (upload speed etc.) applies |
| Mac | Swift 6 (SPM), SwiftUI MenuBarExtra (menu style) | The menu has only a few items; standard OS parts suffice; same idiom as sibling menu bar apps |

- One repository holding `firmware/` and `mac/`, so both sides share the format specification and test vectors.
- Measurement code is copied from existing tools (not a shared library): CPU and GPU from
  load-spinner, network counters (handling of 32-bit wrap and 1 KiB rounding) from net-meter,
  together with their tests.
- GPU usage is read from an undocumented key in IOKit's IOAccelerator `PerformanceStatistics`
  (as load-spinner does). The functions called are public API; if the key is missing, GPU is
  sent as absent and the M5 hides the GPU display.
- With no PSRAM, drawing uses per-region buffers rather than a full-screen buffer (free memory measured in Phase 0).

**Existing tools it complements**

- Same family as load-spinner (a sense of CPU/GPU load in the menu bar) and net-meter (interface traffic).
  Those live on the Mac's screen; m5-system-panel is a permanent instrument off the screen.
- "What is keeping the Mac busy" is left to Activity Monitor (the same line load-spinner draws).

**OS-managed roles (ADR-023 item 3): none**

- The M5 becomes neither a keyboard, a Bluetooth device nor a notification receiver. To the Mac it is only a TCP peer on the same network.
- The only thing the companion obtains from the OS is the local network permission (§5).

**Why Wi-Fi, and the rejected transports**

| Option | Why rejected |
|---|---|
| USB serial | The BASIC's ESP32 has no USB; its only USB data path is CH9102 → UART0, shared with the debug and flashing port. Boot-log interference, resets or a stuck download mode through DTR/RTS, contention with flashing tools, and the risk of opening other ESP32 boards cannot be avoided structurally |
| BLE | Re-enters the area where the withdrawn m5-notify-deck failed (library defaults, OS behaviour) |

**Rejected ways to configure Wi-Fi**

| Option | Why rejected |
|---|---|
| `config.json` on the TF card | Measured by the maintainer: the Mac cannot write to the FAT32 TF card (reads but does not write); writing only works through a Windows VM |
| Browser setup page (192.168.4.1) | Cannot hand the key to the companion safely (a key in a URL stays in the browser history) |
| Automatic captive-portal page | The standards (RFC 8908/8910) require HTTPS and forbid IP literals, which the M5 cannot meet; the alternative (answering all DNS names with the M5) relies on detection Apple does not document, which ADR-023 rules out |
| Espressif's phone app / WPS / typing with three buttons | Reintroduces BLE and needs a phone / often disabled on routers / impractical input |

**Rejected ways to handle spoofing and cross-talk**

| Option | Why rejected |
|---|---|
| Accept fake values from the same LAN | An instrument that can be spoofed cannot be trusted (maintainer's decision) |
| Show a code on the M5 at first connection and type it on the Mac (AirPlay style) | A key exchange resistant to eavesdropping and man-in-the-middle needs a PAKE (SRP, SPAKE2+, …), which CryptoKit lacks; it would mean writing cryptography ourselves |
| Authentication only (no encryption) | Costs about the same, so the content is hidden too |

**Out of scope**

- Notifications, temperatures and fans (only reachable through the private SMC), process lists
- Controlling the Mac from the M5
- Manual IP entry, enterprise Wi-Fi (802.1X), hidden SSIDs, 5 GHz
- Several panels on one Mac, one panel shared by several Macs (neither causes cross-talk, but neither is offered)
- A settings screen on the M5; setup from an iPhone or other devices
- Operating systems other than macOS; Intel Macs

## 4. Development Plan

### Phase 0: Measure the premises (before the design is fixed)

Following ADR-023, behaviour the documentation does not state is observed on real hardware
before the design is fixed. Results go into an ADR and settle the "Phase 0" rows of the state table in §7.

1. Free memory on the M5 with Wi-Fi and drawing running together
2. The setup flow: joining the setup Wi-Fi → whether the Mac returns to its usual Wi-Fi → Known Networks entry and how to remove it
3. Bonjour discovery and the local network permission dialog (both the allow and deny paths; launched with `open`)
4. The TCP connection after sleep and wake, and the M5 switching connections
5. Whether the Mac notices within 5 s when the M5's power is pulled
6. Whether the GPU key can be read on this Mac
7. The conditions under which the M5's hardware RNG is fit for key generation (documentation, and behaviour with Wi-Fi enabled)

Review: the ADR and the state table are reviewed at the end of Phase 0.

### Phase 1: Core

- The format specification (frames, version, use of cryptography, setup exchange) and test vectors
  shared by both sides (known answers, including the RFC 8439/5869 vectors). **The specification alone
  is reviewed before implementation**, including an independent check against RFC 8439 that nonces are never reused.
- Mac: measurement (CPU, GPU, memory, network), discovery / connection / reconnection, cryptography, setup window, menu.
- M5: setup mode, joining the home Wi-Fi, mDNS, receive / verify / acknowledge, page ① Overview, waiting-for-data display.
- Tests: on the Mac, unit tests cover measurement, format, cryptography and state transitions. On the M5,
  a test sketch on the device checks format and cryptography against the test vectors. Cross-talk scenarios are reproduced with a simulated panel on the Mac.
- An end-to-end run on real hardware with the final code.

### Phase 2: Features

- Pages ②–④, buttons, dimming, launch at login, unregistering the panel.
- Reviewable on its own.

### Phase 3: Release

- README (English and Japanese), AGENTS.md, CHANGELOG.
- Developer ID signing and notarisation of the companion (same procedure as the sibling menu bar apps), Homebrew cask.
- Firmware distribution: a merged `.bin` and esptool instructions so users without an Arduino environment can flash it
  (the upload speed stated explicitly, as measured in the knowledge base).
- Integration into lab-series, org catalogue update, check-org.sh.

## 5. Required API Scopes / Permissions

- **macOS local network permission** (since macOS 15; TN3179). The OS shows a dialog at the first Bonjour
  browse or connection. Info.plist declares `NSLocalNetworkUsageDescription` and `NSBonjourServices` (`_m5-system-panel._tcp`).
  - If denied, the menu says permission is required and where to grant it.
  - **On macOS this permission cannot be returned to the undetermined state** (TN3179).
- Keychain: only the app's own items (no additional entitlement).
- Not sandboxed, so no entitlements are needed.
- OAuth, API permissions, IAM for external services: none.

## 6. Series Placement

Series: lab-series
Reason: An experimental project that fixes a protocol and behaviour by measuring them together with
self-built hardware. The existing M5 projects (m5-clock, m5-vehicle-logger) live here too.

## 7. External Platform Constraints

### Mac (macOS 26 or later, Apple Silicon)

| Constraint | Source | Effect on the design |
|---|---|---|
| Local network permission is required for Bonjour browse/resolve and TCP to LAN addresses | TN3179 | §5. On denial NWBrowser reports `PolicyDenied` and NWConnection enters `.waiting` (`localNetworkDenied`); both are mapped to the status display |
| The permission cannot be reset to undetermined | TN3179 | Choice of test machine (see "Test environment") |
| Launching the app binary directly from Terminal is granted automatically | TN3179 | Tests always launch with `open` |
| Joining the setup Wi-Fi once adds it to Known Networks with auto-join, synced through iCloud Keychain; the most recently joined network has the highest priority | Apple Support (Known networks, Wi-Fi priority) | Setup ends by explaining how to remove it; after tests it is removed with `networksetup -removepreferredwirelessnetwork` |
| Whether the Mac rejoins its previous Wi-Fi after the setup Wi-Fi disappears is not stated | Not documented | Observed in Phase 0 |
| Whether a TCP connection survives sleep is not documented | Not documented | Check and re-establish on wake; observed in Phase 0 |
| How long before a silently vanished peer makes the connection fail is not documented | Not in the NWConnection documentation | Detected by the M5's 1 s acknowledgements and a 5 s cutoff |
| Windowless apps may be App Napped and have timers throttled | Energy Efficiency Guide | Use `beginActivity(.userInitiatedAllowingIdleSystemSleep)` while connected; the documentation intends it for finite work, so the reason for holding it is recorded in an ADR |
| No documented way to read GPU usage | — | Undocumented key, hidden when absent (§3) |

### M5 (M5Stack BASIC v2.7, ESP32, arduino-esp32 3.x / ESP-IDF 5.5)

| Constraint | Source | Effect on the design |
|---|---|---|
| Wi-Fi is 2.4 GHz only; supports WPA2-PSK and WPA3-SAE (including transition mode) | M5 specification, ESP-IDF Wi-Fi Security | 5 GHz-only networks and 802.1X are out of scope |
| Joining a hidden SSID is not documented | Not in the ESP-IDF documentation | Out of scope |
| The SoftAP password must be at least 8 characters | arduino-esp32 source | 12 characters are used |
| Scanning while the SoftAP runs switches to AP+STA, and the AP follows the STA channel | ESP-IDF Wi-Fi guide, arduino-esp32 source | Scan once before starting the SoftAP |
| The Wi-Fi driver stores credentials in NVS in plaintext by default; NVS is not encrypted by default | ESP-IDF NVS and Wi-Fi documentation, arduino-esp32 source | Turn off the library's automatic storage and keep one store of our own. The README states that the key and Wi-Fi password remain in plaintext. Flash encryption is irreversible and not used. Before giving an M5 away, erase the settings or run `esptool erase-flash` |
| No PSRAM (520 KB SRAM) | M5 specification | No full-screen buffer; free memory measured in Phase 0 |
| Buttons A/B/C (G39/G38/G37) take no part in boot strapping; G39 has an erratum for interrupts while Wi-Fi is used | M5 pin map, ESP-IDF GPIO documentation | Read by M5Unified polling, no interrupts; "hold B at power-on" is safe |
| Bluetooth memory is released automatically when Bluetooth is not used | arduino-esp32 source | Nothing to do |
| mbedTLS (ChaCha20-Poly1305, HKDF) ships with ESP-IDF | ESP-IDF | The only cryptography used |

### Network

- Guest networks that isolate clients, and networks that block mDNS, are not supported (stated in the README).
- The only custom part is how standard primitives (ChaCha20-Poly1305, HKDF) are combined; the combination is
  reviewed against the RFCs in the Phase 1 format specification.

### Connection state table

Rows marked "Phase 0" are settled after observation on real hardware.

**M5**

| State | Event | M5 screen | Source |
|---|---|---|---|
| No Wi-Fi settings | Boot | After scanning: setup Wi-Fi name, password, instructions | Specification |
| Any | Hold B at power-on for 3 s | Erase settings and key; enter setup mode | Specification, ESP-IDF GPIO |
| Setup mode | Companion saves the settings | "Connecting" → home Wi-Fi | Specification, Phase 0 |
| Joining home Wi-Fi | Cannot connect | "Cannot connect to Wi-Fi" and how to redo setup (no setup Wi-Fi) | Specification |
| Listening | A connection with the correct key arrives | Display | Specification |
| Displaying | No values for 3 s → N more minutes | Waiting for data → dimmed | Specification |
| Displaying | Another connection arrives and its first frame verifies | Close the old connection, show the new one's values | Specification |
| Displaying | Another connection arrives and does not verify | No change (close the new connection) | Specification |
| Dimmed | Button, or values arrive | Brightness restored | Specification |

**Companion**

| State | Event | Menu | Source |
|---|---|---|---|
| First run | Starts browsing | OS permission dialog | TN3179 |
| No permission | Denied | Permission required (where to grant it) | TN3179 |
| Not set up | An M5 in setup mode is visible on the same network | "Start setup" appears | NWBrowser documentation, specification |
| Set up, searching | The panel with its device ID is found | Connected (panel ID) | NWBrowser documentation |
| Connected | No acknowledgement for 5 s, or one that does not verify | Not responding → reconnect | Specification |

| Connected | Sleep → wake | Check the connection and re-establish it | Apple documentation, Phase 0 |
| Any | Unregister | Not set up | Specification |

### Test environment (ADR-023 "machine state is borrowed")

- Tests run on this Mac (the Mac the panel will be used with). The local network permission is needed
  anyway and is kept (maintainer's decision).
- Removed and recorded after every test: the Known Networks entry for the setup Wi-Fi, the companion's
  Keychain items, the login item registration, and any app placed for testing. Removal procedures are
  checked to work before they are relied on.
- The verification VM has no Wi-Fi and cannot be used for these tests.

## Discussion Log

1. **Restart (2026-09-26)**: The general-purpose notification display (m5-notify-deck, withdrawn) is dropped in favour of
   a panel dedicated to system information. The maintainer set the division of roles: the companion measures and sends,
   the M5 only draws, the buttons only switch pages. Taking no OS-managed role (keyboard etc.) structurally removes the cause
   that consumed most of the previous attempt.
2. **GPU**: No documented way to read it. Agreed to use the same undocumented key as load-spinner, hidden when absent.
3. **Companion form**: Agreed on a minimal menu bar app.
4. **Device**: The same M5Stack BASIC v2.7 as before.
5. **Transport, round 1 (USB serial)**: USB serial was recommended first. The maintainer asked whether the driver in use was
   one installed for M5 development, so it was measured: the connected BASIC (CH9102F, `1a86:55d4`) was bound to the
   OS-bundled AppleUSBCHCOM, and the WCH driver was not loaded. The macOS 26.6.2 verification VM also lists `55d4` in the bundled driver's matching table.
6. **Transport, round 2 (USB serial rejected)**: After Espressif's documentation showed the auto-reset hazards (RTS alone resets,
   DTR alone leaves the chip in download mode), the maintainer judged that sharing the debug port and coexisting with flashing
   is unreasonable. The BASIC's ESP32 has no USB and only one USB data path, so this cannot be avoided structurally; rejected.
7. **Transport, round 3 (Wi-Fi)**: Wi-Fi recommended; BLE not recommended as the area of the previous failure.
8. **Wi-Fi configuration**: The TF card option was rejected on the maintainer's measurement (the Mac cannot write the FAT32 TF card).
   Agreed on the M5 running a setup Wi-Fi with a browser page.
9. **Automatic captive-portal page**: Primary-source research showed the standards require HTTPS and forbid IP literals, which
   the M5 cannot meet, and Apple does not document the detection the DNS alternative relies on; agreed not to use it.
10. **Acknowledgements from the M5**: Because how fast the Mac notices a vanished peer is undocumented, agreed on 1 s
    acknowledgements with a 5 s cutoff.
11. **Test machine**: After being told the local network permission cannot be reset and the VM has no Wi-Fi, the maintainer chose this Mac.
12. **Spoofing**: The draft that accepted fake values from the same LAN was rejected by the maintainer. To share a key,
    setup moved from the browser to the companion, with the key handed over inside the setup Wi-Fi (password lengthened
    to 12 characters to resist brute force). Normal operation uses ChaCha20-Poly1305 for encryption and authentication.
    The AirPlay-style code entry was rejected because it needs a PAKE CryptoKit lacks; handing the key over on a browser page
    was rejected because it stays in the history.
13. **Cross-talk**: The maintainer pointed out that several devices on one network would cross-talk. The earlier state-table row
    "drop the old connection when a new one arrives" was confirmed to cause it (another Mac could cut the connection). Agreed:
    peers are decided by device ID and key, switching happens only when the first frame verifies, and the panel-selection menu is removed.

## Amendments

The body is kept as the record of what was agreed; later changes are appended here.

- **A1 (2026-09-26, scaffolding): repository layout.** §3 says the repository holds `firmware/` and `mac/`.
  Instead, the companion's Swift package sits at the **repository root** and only the firmware is under `firmware/`.
  Reason: the organization's Swift app layout (CONVENTIONS, GUI app scaffold) puts `Package.swift` at the root, and
  check-org.sh check 12b (the cask's macOS floor against `Package.swift`) only reads a root `Package.swift` — under
  `mac/` the check would not fail, it would silently be skipped. The purpose stated in the body, sharing the format
  specification and test vectors between both sides, is unchanged.
- **A2 (2026-09-26, Phase 0 complete): the measurements.** The results of the seven Phase 0 items and what they decide
  (connection supervision; flash layout changed to 16 MB with a 3 MB app; drawing in bands; dimming during sleep is
  required; the setup Wi-Fi clean-up guidance is decided after checking it in Phase 1) are in
  [ADR-0001](adr/0001-phase0-premises.md). The "Phase 0" rows of the §7 state tables are settled there, with four rows added.
- **A3 (2026-09-26, protocol v1): cryptographic primitives and the setup peer.** ChaCha20-Poly1305 is not built into the
  panel's prebuilt libraries, so every ChaCha20-Poly1305 (RFC 8439) in the body reads as **AES-256-GCM (NIST SP 800-38D)**.
  Keys are derived with HKDF-SHA256 Expand only. The setup peer is the Wi-Fi interface's router address over a connection
  pinned to that interface (the body's "the companion finds the M5 in setup mode" uses this, not mDNS). Disruption on the
  LAN (stopping the display) is accepted as a residual risk; showing false values and cross-talk remain impossible.
  Evidence and rejected alternatives: [ADR-0002](adr/0002-crypto-and-setup-binding.md); the exchange in detail:
  [protocol v1](protocol.md).
- **A4 (2026-09-26, measurement implementation): no P/E distinction per core.** Which logical CPU is which kind (P/E) is
  not documented (`sys/sysctl.h` defines only the count per kind and that perflevel 0 is the highest performance); only the
  undocumented IODeviceTree value `cluster-type` tells. The maintainer decided not to distinguish them. Page ② in §2,
  "per-core bars (P / E cores in different colours)", reads as "per-core bars (one colour)". Protocol v1's `cores` carries no type.
