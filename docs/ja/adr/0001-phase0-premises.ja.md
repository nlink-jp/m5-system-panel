## Context

RFP は、文書に無い 7 つの振る舞いを Phase 0 で実測してから設計を確定するとした。
計測コード・手順・生の結果は `spikes/README.md` にある。ここでは結果と、それが決めることだけを書く。
環境は 1 台の Mac（macOS 27.0、有線が主経路で Wi-Fi も同じ LAN に参加）と、電池を積んでいない
M5Stack BASIC v2.7（フラッシュ 16 MB）。回数はいずれも少ない（下の表の「回数」）。

| # | 実測したこと | 回数 |
|---|---|---|
| 1 | Wi-Fi・mDNS・TCP 待ち受けの後の空きは約 155 KB、連続して確保できる最大は 59,380 B。全画面の 16bit バッファ（153,600 B）は確保できない。試験用ファームウェアだけで既定のアプリ領域（1.25 MB）の 88 % | 1 |
| 2 | 設定用 Wi-Fi に参加した瞬間に「記憶したネットワーク」に登録される。設定用 Wi-Fi が消えると約 11 秒で元の Wi-Fi に自動で戻る。`networksetup -removepreferredwirelessnetwork` は登録を消すが、システムのキーチェーンの「AirPort network password」は残る（削除には管理者権限） | 1 |
| 3a | 許可のダイアログ中に作った接続は、許可された後も `.preparing` のまま 2 分以上止まり、自分では再試行しなかった（下位の経路が許可の反映前に「Local network prohibited」で失敗） | 1 |

| 3c | システム設定の一覧には実行ファイル名が表示される | 1 |

## Decision

### 1. コンパニオンの接続の見張り方（3a・3b・4・5）

接続の状態ごとに、次のように扱う。

| 状態 | 扱い |
|---|---|
| `.preparing` が 10 秒続く | 取り消して作り直す（3a と 5 で、OS はこの状態から自分では抜けなかった） |
| `.waiting` | OS の再試行に任せる。エラーが `.dns(-65570)` なら「許可が必要です」を表示する。`unsatisfiedReason == .localNetworkDenied`（文書にある値）も同じに扱う |
| `.failed` / `.cancelled` | 5 秒後に作り直す |
| `.ready` で 5 秒応答なし | 「応答がありません」を表示し、古い接続を取り消して作り直す（OS の判定は約 30 秒かかる） |

- 探索の結果は「パネルがいるか」の判定に使わない（5 で消えも戻りも報告されなかった）。探索は接続先（サービス名）を知るためだけに使い、状態の表示は接続と応答から決める。
- didWake・willSleep で特別なことはしない（4 で、監視と再探索だけで didWake より早くつながった。willSleep の後も通信できる時間がある）。
- 最初の起動は、許可のダイアログとの競合（3a、観測 1 回）に当たり得る。上の `.preparing` の 10 秒で回復するので、特別な扱いは足さない。

### 2. パネルのメモリとパーティション（1）

- ボードの設定を `FlashSize=16M`・`PartitionScheme=huge_app`（アプリ 3 MB、OTA なし）にする。
  OTA は RFP の対象外。試験用ファームウェアだけで既定の領域の 88 % を使ったため。
- 描画用のバッファは 1 枚あたり 51,200 B（320×80、16bit）を上限にし、全画面のバッファは持たない。
- Phase 1 で暗号と描画を載せた状態の空きを測り直す。**置き換えを数百回繰り返す試験**で、付記の減少が
  止まることを確かめる（止まらなければ、接続の扱いを見直す）。

### 3. スリープ中のパネル（4）

スリープ中も USB 給電は続き、画面は点いたままになる。RFP の「データ待ちが続いたら暗くする」は必須とする。

### 4. 設定用 Wi-Fi の後始末の案内（2）

設定の窓の最後に出す消し方の案内は、`networksetup` の方法ではパスワードがシステムのキーチェーンに残るので使わない。
システム設定の「リストから削除」がパスワードまで消すかは未測定。**Phase 1 で設定を通しで試すときに、その方法で消して
キーチェーンを確かめてから**、案内の文面を決める。

### 5. そのほか

- 鍵と使い捨てパスワードは、Wi-Fi を起動した後に作る（7）。
- GPU は RFP どおり（6）。確かめたのはこの Mac の 1 機種だけ。
- コンパニオンの実行ファイル名 `M5SystemPanel` は、システム設定の一覧に出る利用者向けの名前として扱う（3c）。

### 状態表の変更（RFP §7 への反映）

コンパニオンの表に次の行を加える。「Phase 0」だった行は上の決定で確定する。

| 状態 | 出来事 | メニューの表示 | 根拠 |
|---|---|---|---|
| 探しています | 接続が `.preparing` のまま 10 秒 | 探しています（作り直す） | 実測 3a・5 |
| 接続中 | 許可が取り消される | 許可が必要です（接続は POSIX 53 で切れる） | 実測 3b |
| 許可なし | 許可が戻される | 接続中（`.waiting` の接続を OS が再開） | 実測 3b・TN3179 |
| 接続中 | スリープ → 起床 | 接続中（5 秒監視と再探索で、didWake より前に回復） | 実測 4 |

## Consequences

- コンパニオンは、接続を 1 本ずつ状態で見張る小さな状態機械を持つ。時間（10 秒・5 秒・5 秒）は注入できるようにして、
  単体テストで状態の遷移を確かめる。
- パーティションの変更で、以前に書き込んだファームウェアとは領域の配置が変わる。書き込みは消去からやり直す前提にする。
- 回数が 1 の観測が多い。とくに 3a（許可の競合）と 4（スリープ）は、Phase 1 の通し試験で再び観測できたら記録を足す。
- macOS 26 では何も測っていない（検証用 VM に Wi-Fi が無い）。最小 OS を 26 のままにするなら、26 の実機で
  3・4・5 を確かめるまで README に書かない。

## Alternatives considered

| 案 | 採らない理由 |
|---|---|
| `.waiting` も時間切れで作り直す | 3b で OS は `.waiting` から自分で戻った。作り直すと、その再開を取り消すことがある（実際に 1 回起きた） |
| 探索の `removed` / `added` を見て状態を表示する | 5 で電源断を 2 分以上報告しなかった |
| didWake で接続を作り直す | 4 で、didWake が届く前に監視がつなぎ直していた。二重の作り直しになる |
| 既定のパーティションのまま、機能を削って収める | 試験用だけで 88 %。暗号・描画・4 ページを載せる余地がない |
| OTA ありの 8 MB 構成（アプリ 3 MB × 2） | OTA は対象外。使わない領域を確保するだけになる |
